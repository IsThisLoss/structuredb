# StructureDB development roadmap

This roadmap is an engineering assessment of the repository, not a production-readiness certification. It is based on a static review of the current code, documentation, protocols, and tests; the tests were not run as part of this assessment. Priorities assume a small, learning-oriented project that values understandable internals and safe evolution over feature count. Estimates and SLOs should be set after collecting a baseline.

## Recommended direction

1. Establish storage, recovery, and transaction invariants before relying on them for distributed features.
2. Deliver automatic asynchronous follower bootstrap and catch-up with an explicit readiness contract. This solves the requested one-leader-to-many-read-replicas use case without promising leader failover or zero data loss.
3. Build request routing and static sharding on those foundations. Introduce a fault-tolerant control plane and shard movement only after the single-shard experience works.
4. Prototype JavaScript early in isolation, but expose writes only after execution limits and transaction semantics are defined. Initially restrict distributed scripts to one shard.

The streams can overlap in design and prototypes. The dependencies above are release gates, not a requirement to finish every item in one stream before starting another. Maintain small vertical slices that run end to end.

## 1. Codebase assessment and foundation

### Strengths

- A real end-to-end path exists: LSM memtables, SSTables, compaction, WAL, recovery, transactions, gRPC, SDK and CLI. The [README](../README.md) and [replication guide](replication.md) explain the architecture and current operating model.
- The storage/transaction boundary keeps MVCC policy above the storage engine; [async I/O and coroutine-friendly primitives](../src/server/io/) give the project a consistent concurrency model.
- Pages have checksum validation, and the viewer, system views, configuration, and operational documentation are useful foundations for diagnosing behavior.
- [Integration fixtures and scenarios](../tests/integration/tests/) exercise transactions and replication with real server processes, alongside focused unit tests. Follower streaming already has reconnect and connected-follower retention concepts.

### Risks and weaknesses

| Priority | Evidence and impact | Next action |
| --- | --- | --- |
| P0 | [FileWriter::FSync](../src/server/io/file_writer.cpp) invokes `fsync` on the event-loop thread and ignores its return value. [WAL writes](../src/server/wal/writer.cpp) depend on it. A failed sync can be reported as success and a slow sync can stall unrelated work. | Move sync to the blocking executor, propagate errors, handle short writes and test failure injection. Specify what an acknowledged commit guarantees, including file and directory metadata persistence. |
| P0 | [WAL reader](../src/server/wal/reader.cpp) catches generic recovery errors, logs and stops reading a segment. Corruption or partial records could be mistaken for a valid end; the exact consequences need tests. | Introduce explicit framed, versioned records with lengths/checksums and a precise rule for incomplete final tails versus corruption. Fail closed on unexpected corruption; test torn writes, damaged middle records and I/O errors. |
| P0 | [Transaction commit](../src/server/transaction/storage.cpp) marks a transaction committed before awaiting its WAL write. Coroutine interleaving or failure may expose a commit before durability; confirm with a targeted concurrency test. Locks have no visible deadlock/timeout policy. | Define commit linearization and crash semantics, publish visibility only at the safe point, and add conflict, deadlock, cancellation, and failure tests. | P1 | [Follower guide](replication.md) requires WAL from segment 0 or a manual copy, recommends a potentially inconsistent live copy, and permits local reads before an explicit catch-up barrier. [Streaming](../src/server/services/replication_service/replication_service.cpp) ships growing page tails and advances retention based on sending rather than a durable follower acknowledgement. | Replace live-copy advice with a consistent checkpoint protocol; prove gap detection, acknowledgement and readiness behavior. | P1 | [LSM options](../src/server/lsm/options.hpp) limit a record to a page and define a per-SSTable page cache; flush/compaction and WAL shipping lack an established resource budget. Growing tails are repeatedly scanned and sent. | Measure memory, read/write amplification, compaction debt and lag. Add bounded queues, backpressure, size limits and a global cache budget as needed, based on measurements. |
| P1 | Interfaces such as [StorageEngine](../src/server/table/storage/storage.hpp), [DurableStorage](../src/server/table/storage/durable_storage.hpp) and [Table](../src/server/table/table.hpp) support hypothetical alternatives and include default no-op capabilities. | Audit call sites and consumers. Keep boundaries that isolate real policies, testing seams or durability; collapse single-implementation layers where they make invariants harder to follow. Make required operations explicit rather than silently succeeding. Avoid a wholesale rewrite. |

| P2 | Existing integration tests cover useful happy paths, but the reviewed scenarios do not establish crash consistency, storage corruption behavior or behavior during network partitions and snapshot installation. | Expand deterministic fault-injection, randomized model tests, sanitizer builds and benchmarks. |

### Foundation milestones

- **F0 — Contract and reproducibility:** write a short invariants document for acknowledged commits, ordering, recovery, snapshot isolation, single-thread executor assumptions, file formats and supported record sizes. Make clean build/tests and sanitizer runs reproducible in CI; record a workload baseline (throughput, p50/p95/p99 latency, memory and disk use). Audit existing CI before adding jobs.
- **F1 — Durable writes and recovery:** implement the P0 fixes, including atomic file installation and directory sync where required by the chosen filesystem contract. Add tests at each write/sync/rename boundary, short writes, failed sync, torn WAL tail, corrupted non-tail and restart. A test must distinguish acknowledged commits from indeterminate in-flight requests; never require an unacknowledged request to be absent.
- **F2 — Transaction and storage correctness:** check visibility, read-your-writes, write conflicts, rollback, concurrent transactions, DDL and restart against a reference model. Test compaction with active snapshots and tombstones, cancellation, repeated writes and lock cycles. Define deadlock handling/timeouts. Correct failures before making stronger guarantees.
- **F3 — Simplify and bound:** remove only abstractions proven unnecessary, introduce bounded scans, queues and memory, then benchmark flush/compaction and add metrics. Gate further optimization on a measured bottleneck. Document compatibility or migration for on-disk/WAL changes.

**Exit:** under injected process crashes and I/O errors, all acknowledged commits survive according to the documented contract; recovery either reconstructs valid state or reports corruption explicitly. Tests also demonstrate the documented transaction behavior. Process-kill tests alone do not prove power-loss durability.

## 2. Cloud-native read replication

**Initial contract:** one explicitly configured leader, any number of asynchronous read-only followers, no automatic failover. An acknowledged leader write may be lost if the leader fails before replication. Follower reads can be stale even after readiness. `Ready` means the follower has applied a leader high-water mark sampled during its join, not that it stays up to date forever. Expose lag and optionally a maximum-lag readiness policy; fail closed if the leader is unavailable during initial catch-up. Provide explicit stale-read behavior for later disconnection.

1. **R0 — Protocol and invariants.** Define cluster/node identity, immutable leader epoch/history, ordered log position, record framing, applied vs received vs durable positions, gap detection, reconnect and duplicate replay behavior. Require leader to reject an unavailable requested position with `snapshot required` rather than silently skipping. Design version negotiation and metadata to prevent joining the wrong cluster or history. Instrument bytes, positions, lag, state, errors and retention.
2. **R1 — Consistent checkpoint.** Create a checkpoint with a manifest for catalog, committed transaction state and data files at one logical boundary. Atomically pin the required files and all log after that boundary before cleanup can delete them. Clarify handling of in-flight transactions and file lifetimes during compaction. Transfer bounded chunks with sizes and checksums to a temporary directory; verify and atomically install, persist installation metadata, then resume log replay at exactly the specified boundary. Release pins on success, expiration or cancellation with bounded retention and restart cleanup. Do not copy a live directory blindly.
3. **R2 — Automatic join and catch-up.** On empty or too-far-behind follower, request checkpoint, install it, then apply a continuous ordered WAL stream. A durable applied cursor and explicit acknowledgements govern retention; ensure crash/replay is idempotent. Track `initializing → snapshotting → catching_up → ready` and `failed/retrying`. Once it has applied a leader barrier sampled after installation, enable reads. Make repeated startup and interrupted transfers safe.
4. **R3 — Operational robustness.** Add exponential backoff with jitter, bounded retention/slow-follower policy, quotas, TLS/authentication, cancellation, health/readiness endpoints, and dashboards for lag, snapshot age, bytes and errors. Validate create/drop including empty tables, transactions spanning the checkpoint, large data, restarts at every install step, concurrent compaction/cleanup, duplicate pages, network breaks and leader restart. The test must compare the complete follower state to the leader at a known barrier, not only one key.
5. **R4 — Optional high availability, separate project.** If automatic promotion becomes a goal, select a proven consensus implementation, introduce quorum-backed leadership/terms, fencing and durable membership changes, and specify write/read consistency, split-brain behavior and data loss. Existing asynchronous WAL shipping alone cannot safely elect a leader. A single voter can start alone but has no failure tolerance; safely adding voters changes quorum and availability. See the [Raft paper](https://raft.github.io/raft.pdf).

**Exit:** start an empty follower using only the leader address after old WAL has been cleaned, while writes and compaction continue; it becomes ready and matches a known leader barrier. Repeat with transfer interruption, follower/leader restart and retention pressure, without missing acknowledged data covered by the snapshot and replay contract.

## 3. Database-level sharding

**Initial contract:** any configured server accepts a client request and routes it to the correct shard leader. The first release uses a single replica per shard or the asynchronous followers above; it provides no automatic shard failover. Begin with point operations and single-shard transactions, rejecting cross-shard transactions explicitly. Reuse the existing API where possible while returning precise retry/unsupported errors.

1. **S0 — Partitioning and API design.** Define stable shard IDs and key encoding. Prefer range partitions initially because the API already supports ordered scans; document hot-spot tradeoffs versus hashing. Specify inclusive/exclusive boundaries, pagination, table creation, error/retry and read consistency. Separate routing metadata from user records and define ownership epochs. Define transaction affinity at begin/first operation and reject a later operation targeting another shard.
2. **S1 — Static routing vertical slice.** Use versioned operator-supplied topology first: table/range → shard → leader. The receiving server executes locally or proxies with deadline, cancellation, hop limits and structured errors; detect stale epoch and retry only safe operations. Add request IDs and durable deduplication before claiming mutation retries are safe after an ambiguous outcome. Test routing through every node, node failure, stale topology and client compatibility.
3. **S2 — Distributed reads.** Split scans by range, issue bounded parallel requests, merge in key order, paginate, and propagate cancellation. Specify a consistent snapshot or explicitly document that a fan-out scan is not a global snapshot. Bound memory, response sizes and concurrency; test boundary keys and partial failures.
4. **S3 — Metadata and membership.** Replace static configuration with a versioned control plane for node identity, shard ownership and configuration. A single-node metadata service is a learning step, not HA. Before automatic ownership changes or failover, use a consensus-backed metadata group, fencing epochs and an explicit loss-of-quorum behavior. Ensure stale routers refresh safely and cannot allow two owners to accept writes.
5. **S4 — Online split and movement.** Reuse the checkpoint-plus-log mechanism per shard, then fence the old owner and atomically publish the new ownership epoch after catch-up. Persist migration state and resume or roll back safely on crashes; test writes during copy, duplicate requests, source/destination loss and partitions. Add placement and balancing policies only after manual moves are correct.
6. **S5 — Advanced semantics.** Evaluate distributed transactions, global snapshots and secondary indexes only when concrete workloads justify the complexity. If added, specify transaction coordinator recovery, isolation and availability under partitions first; do not silently degrade atomicity.

**Exit:** with two statically configured shards, clients connect to either server, point operations and single-shard transactions work correctly, cross-shard transactions fail explicitly, and ordered paginated scans cover shard boundaries under the documented consistency model. Online moves and HA have separate later exit gates.

## 4. Embedded JavaScript

**Initial contract:** a client executes a bounded script against one local shard through a minimal database API. Mutating scripts run in one transaction; success commits once, exceptions/timeouts/cancellation abort. No filesystem, network, process, native modules or arbitrary host access. Replicate the resulting committed writes through the database WAL, not script re-execution; timestamps and randomness therefore cannot cause divergent replicas. Scripts may return only bounded serializable values.

1. **J0 — Spike and choose runtime.** Compare embeddable engines for build/maintenance burden, license, embedding API, interrupts, memory accounting and platform support. [QuickJS](https://bellard.org/quickjs/quickjs.html) is a sensible first candidate: its documented C API includes memory limits and an interrupt handler. Verify the precise version, license and behavior in a small prototype; engine limits alone are not a security boundary.
2. **J1 — Isolated execution.** Run scripts on bounded worker threads or, for untrusted code, a separately constrained worker process with OS isolation. Never execute arbitrary CPU-bound JS on the Asio event loop. Set CPU/wall deadline, memory, stack, input/output size and concurrency limits; implement cancellation and test infinite loops, allocation bombs, engine crashes and host-call timeouts. Avoid enabling QuickJS `std`/`os` modules. Define process recovery and communicate deadlines to all host operations.
3. **J2 — Database API and transaction.** Expose a small async `get`, `put`, `delete`, and bounded `scan` API using the normal database/transaction path. Specify promise scheduling and the safe bridge between worker and coroutine executors; ensure no worker blocks the event loop. Abort on uncaught exception, timeout, disconnect or host error, and handle an ambiguous commit response explicitly. Include authorization on every host call, and test atomicity and conflicts.
4. **J3 — RPC and usability.** Add versioned execute request/response, typed result/error encoding, client SDK and CLI support, documented examples and metrics. Enforce source/result limits, permissions and rate limits. Start with per-invocation source; add stored, versioned procedures only if needed, including ownership and rollout semantics.
5. **J4 — Sharded behavior.** Require a shard key and route the entire invocation to its owner. Reject calls that reach outside that shard and ensure migration/fencing rules apply. Cross-shard scripts and distributed atomicity require S5 and a separate design.

**Exit:** a script atomically reads and updates a key, rolls back on exception or timeout, does not stall normal traffic during an infinite loop, survives leader restart through ordinary WAL recovery, and produces identical follower data without re-running the script.

## Delivery and tracking

Use four GitHub parent issues (Foundation, Read replication, Sharding, JavaScript) and milestone sub-issues matching the IDs above. Decompose each milestone into independently reviewable vertical slices; keep the next few ready to implement and leave distant work at milestone granularity. Use GitHub issue dependencies for actual blockers and link PRs using closing keywords. [GitHub sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues) and [Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/quickstart-for-projects) support this hierarchy and board views.

A lightweight project board can use `Backlog`, `Ready`, `In progress`, `Blocked`, `Review`, `Done`; fields: stream, priority, milestone and optional size. Mark blocked issues with their specific dependency. Prefer a small number of issues in progress; review the board periodically and record decisions in short design documents. A milestone is done only when its exit criteria, tests, documentation and any format/protocol upgrade notes are complete. Track runtime indicators separately from work status: recovery failures, fsync latency/errors, compaction backlog, replication state/lag, routing errors, and script limits/timeouts.

Suggested first issues:

1. Document write, commit, recovery and replication invariants (F0).
2. Add failure injection around WAL write and sync; move and check `fsync` (F1).
3. Detect and report WAL corruption separately from incomplete final tails (F1).
4. Reproduce commit visibility during delayed/failed WAL sync and fix the observed behavior (F2).
5. Design and test checkpoint boundary, WAL pinning and follower join state machine (R0/R1).
6. Prototype QuickJS limits and worker isolation without database access (J0/J1; independent spike).
7. Design range ownership, routing epochs and single-shard transaction behavior (S0).

Do not infer completion from issue count or make calendar commitments before a baseline. No GitHub issues or project were created by this document.
